===============================================================

Fecha: 2026-10-29. Rama DC-002. Antes: DC-002.66 (139 de 139 paquetes compilan a .gox).

LA PREGUNTA
-----------
DC-002.66 probo que el motor COMPILA para sh-elf. Compilar no es enlazar. Antes de escribir una linea de
backend de render hay que saber si esos .gox se pueden unir con KOS + libgodc en un 1ST_READ.BIN que arranque
en Flycast, y cuanto ocupa. Tres pasos: (1) que es y que cubre el stub de ebiten, (2) el binario minimo con un
paquete del motor, (3) d2ui + d2gamescreen referenciados.

RAM (lo que de verdad decide, medido en la consola)
--------------------------------------------------
    En los dos pasos el monton de KOS tiene un arena de ~4,36 MB (ahi viven los dos semiespacios de GC de
    libgodc, 2 MB cada uno, que se llevan casi todo) y de libre quedan 1.400 B / 3.512 B. Ese numero NO dice
    la RAM libre: dice que el arena esta lleno. La RAM se mide al reves, pidiendole al monton el bloque que el
    motor va a necesitar:

    bloque pedido        paso 2 (1,37 MB)     paso 3 (11,66 MB)
    4 MB                 4.194.304 OK         0  FALLA
    1 MB                 1.048.576 OK         0  FALLA
    1.228.800 B (la pantalla 640x480 RGBA del motor)  1.228.800 OK    0  FALLA
    256 KB               262.144 OK           262.144 OK

    O sea: el paso 3 arranca y ejecuta el motor, pero NO puede reservar ni 1 MB. La pantalla que el motor pide
    (1,2 MB) no entra. Enlazar los 125 paquetes deja la consola sin RAM para dibujar: sirve como prueba de
    enlace, NO como binario de juego.

LO QUE ESTO CAMBIA PARA LA FASE B (render)
------------------------------------------
1. El enlace esta resuelto: no hay simbolos faltantes ni problemas de ABI. El bloqueo no era el enlazador.
2. El enemigo es el TAMANO. 11,12 MiB de 16 MB con el motor entero: no queda RAM para la pantalla ni para las
   texturas de ningun tamano util. El siguiente paso NO es "escribir el backend", es RECORTAR el binario:
   - los .gox traen DWARF (11,3 MB de los 40,6 del ELF): no va al BIN, pero compilar con -g0 achica los
     objetos y el tiempo de enlace;
   - gccgo mete el .text de cada paquete entero: hace falta -ffunction-sections al compilar los .gox y
     -Wl,--gc-sections al enlazar para que el linker tire lo que no se usa (medido: hoy no se tira nada);
   - y las 33 GamepadButton/stubs de ventana vacios son ruido: no hay nada que ganar ahi.
3. El stub de ebiten ya tiene rasterizador por software + subida de pantalla completa al PVR (C, 463 lineas):
   el que escriba el backend de sprites/tiles arranca de ahi, no de cero.

PITFALLS MEDIDOS EN ESTA TARJETA
--------------------------------
- `cp -rs` sobre un arbol de enlaces que ya existe dice "son el mismo fichero" y mezcla el arbol: el script
  arma el arbol de enlace desde cero en cada corrida.
- `stat -c%s` sobre un enlace simbolico mide EL ENLACE (69 B por un .gox de 1 MB). Hubo que usar stat -L.
- gccgo NO respeta //go:build: serial_dc.go lleva //go:build dreamcast y gccgo lo compila igual; `go run` en el
  host lo salta. Asi el mismo main.go sirve para las dos puntas.
- Cuando main retorna, libgodc llama a arch_exit de KOS y Flycast (sin BIOS) reporta
  "Fatal: SH4 exception when blocked" ~0,5 s despues de imprimir: parece un crash del enlace y no lo es. El POC
  se queda en un bucle (kos.ThdSleep) y la corrida termina por el script.
- La etiqueta __arch_mem_top de KOS (startup.S) NO resuelve al enlazar desde C: "undefined reference to
  __arch_mem_top". Por eso la RAM se mide pidiendo bloques con malloc, no leyendo el techo.
- El ELF no es el tamano que importa: 40,6 MB de prog.elf son 11,66 MB de BIN. Lo que va a RAM es el BIN.
