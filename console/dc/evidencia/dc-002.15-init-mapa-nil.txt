==============================================================================
[2] LA CAUSA: ORDEN DE LOS init() ENTRE ARCHIVOS (no es una garantia del lenguaje)
==============================================================================

d2common/d2skill/class.go decia:

    var doTable map[int]doFn          <- nil
    func init() { doTable = map[int]doFn{ ... } }

y d2common/d2skill/class_abc.go:

    func init() {
        doTable[15] = doDopplezonFn   <- linea 17: aqui murio
        ...
    }

con este comentario en class_abc.go (lineas 10-12):

    "The registration lives here (not in the table of class.go) so the class files of the other classes
     stay untouched; Go runs the init functions of a package in file name order and "class.go" comes
     before this file."

Esa ultima parte es comportamiento de la HERRAMIENTA de Go, no del lenguaje: el spec garantiza que la
inicializacion de las VARIABLES del paquete termina antes de que corra cualquier init(), y del orden de
los init() de un paquete solo dice que van "en el orden en que son presentados al compilador" (y pide a
los sistemas de build que los presenten en orden de nombre de archivo).

Medido: la linea de compilacion SI presenta los archivos en orden (build-motor-all.sh usa `ls *.go`, que
ordena), pero gccgo numeró el init de class_abc.go como `..init0`, o sea PRIMERO (addr2line del punto 1):
el orden de los init de archivo no es el orden de la linea de compilacion. Con el init de class_abc.go
adelante, el mapa todavia era nil.
