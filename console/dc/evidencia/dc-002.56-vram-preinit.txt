DC-002.56 -- EL PVR APAGADO: las tres lecturas de VRAM del camino previo al video
==================================================================================
Fecha: 2026-10-27.  Rama DC-002.  Host: CachyOS, Flycast 2.7 (AppImage), sin KVM.
Todo lo de abajo esta medido en este host, con los scripts de `scripts/console/`.

VEREDICTO, PRIMERO
------------------
"La lectura pre-init era la causa" -> **NO**. Con dos pruebas duras:

  1. Con el PVR apagado `pvr_mem_available()` devuelve 0 y NO toca nada: corta con `if(!pvr_mem_base)
     return 0;` sobre un estatico en .bss, antes de mirar el allocator o `pvr_state`. El sospechoso que
     quedo listado en dc-002.53 (10.g.3), "eso dejaria al allocator del PVR con estado sucio justo antes
     de pvr_init_defaults", no ocurre: la funcion ni siquiera llega al allocator.
  2. Sacando las tres lecturas del camino previo al video NO se arregla nada: BESTIA=1 sigue muriendo. Y
     ademas el cambio mueve el layout del binario y TUMBA a BESTIA=0 (el control que dibuja). Medido con
     el mismo arbol y los mismos scripts: 4 corridas clasificadas + 1 control de 1 byte.

1) LA MEDICION DEL SOSPECHOSO (antes de tocar codigo)
----------------------------------------------------
Header de KOS: `~/dreamcast/kos/kernel/arch/dreamcast/include/dc/pvr/pvr_mem.h`
  `size_t pvr_mem_available(void);`  -- "Return the number of bytes available still in the PVR RAM pool."

Implementacion: `~/dreamcast/kos/kernel/arch/dreamcast/hardware/pvr/pvr_mem.c:169-182`

    static size_t pvr_mem_available_int(void) {
        struct mallinfo mi = pvr_int_mallinfo();
        return mi.arena - mi.uordblks;
    }
    size_t pvr_mem_available(void) {
        if(!pvr_mem_base)                 <-- ACÁ CORTA
            return 0;
        return pvr_mem_available_int() + (PVR_RAM_INT_TOP - (size_t)pvr_mem_base);
    }

  * `pvr_mem_base` es un `static pvr_ptr_t` de ese archivo (linea 57) -> .bss, cero al arrancar; solo lo
    llenan `pvr_init`/`pvr_mem_reset`. Con el PVR apagado la funcion retorna 0 en la primera linea.
  * `pvr_mem_available_int()` (la que mira el allocator) NO se ejecuta en ese caso.
  * En este KOS el allocator de VRAM es un dlmalloc propio (`pvr_mem_core.c`, "a dlmalloc-derived malloc
    for use with the PVR memory pool"). La version vieja de la API que la tarjeta sospechaba, con
    `pvr_state.ram_free_list`, NO EXISTE en este arbol:
        grep -rn "ram_free_list" ~/dreamcast/kos/kernel/arch/dreamcast/{hardware,include}/
        (sin resultados)
  * El numero de la consola lo confirma: `HITO238: MAPA-IMAGEN ... vram_libre= 0` es exactamente el 0 del
    early-return, no un allocator con estado raro.
  * Contraste con el PVR ENCENDIDO, ya medido en este repo (dc-002.36-menu-consola.txt:83):
        "texturas subidas a la VRAM: 10 de 11   (bytes= 1196032, vram_libre= 4593064)"

Conclusion de la medicion: la lectura pre-init es un 0 constante y sin efectos. No ensucia el allocator,
no escribe en `pvr_state` y no puede ser la causa de la excepcion dentro de `pvr_init_defaults`.

3) EL UMBRAL: menos de 64 bytes (esto es lo que cierra la discusion)
--------------------------------------------------------------------
Mismo arbol, misma bandera (BESTIA=0), 4 binarios distintos en 1ST_READ.BIN:

    1.851.848 B  arbol del commit 7adb9717 (antes de esta tarjeta)      -> ANDA    (cuadros=9)
    1.851.848 B  ese mismo arbol + UNA edicion de 1 byte en una cadena  -> ANDA    (cuadros=9)
                 (`"HITO238: hay control en el puerto 0"` -> `... puerto 0."`: el binario NO cambia de tamano)
    1.851.784 B  con la limpieza (sin VRAM-POSTINIT)                    -> COLGADO (cuadros=0)
    1.851.880 B  con la limpieza + VRAM-POSTINIT                        -> COLGADO (cuadros=0)

O sea: el disparador no es "cuanto trabajo hace el POC antes del video" (los dos que dibujan y los dos que
se cuelgan hacen EXACTAMENTE el mismo trabajo), es donde caen las cosas en el binario. El escalon medido
es de 64 bytes, que es justo el paso con que se mueve 1ST_READ.BIN. Es la firma de DC-002.53 ("es la forma
del binario, no la logica del bicho"), ahora con el numero: 64 bytes deciden entre dibujar y colgarse.

Por eso la limpieza NO se aterrizo en el POC: dejaria el control (BESTIA=0) roto. El arbol queda con las
tres lecturas como estaban, y con la nota de por que (main.go ~930 y ~1171, cshim.c d2c_vram_libre).

6) INSTRUMENTO: el clasificador contaba mal la excepcion
--------------------------------------------------------
`checar-arranque-253.sh` solo contaba la sonda `ARQ-PILA253-REAL` (de DC-002.53). En este arbol la sonda no
esta compilada, asi que BESTIA=1 —que muere con `Unhandled exception: PC 8c42e020, code 1, evt 0180`— salia
clasificada COLGADO. Ahora cuenta tambien los `Unhandled exception` del log de Flycast y los imprime:

    -- ojo: 1 'Unhandled exception' en el log (sonda ARQ-PILA253-REAL: 0)
    == estado: MUERE-EXCEPCION
    Unhandled exception: PC 8c42e020, code 1, evt 0180

(Nota: `resolver-pc.py` necesita el toolchain en el PATH; sin `env.sh` muere con `FileNotFoundError:
sh-elf-nm`. Con el entorno cargado resuelve el PC de la muerte a DATOS, no a codigo:
    $ . scripts/console/env.sh && python3 scripts/console/resolver-pc.py /tmp/dcbuild/vram56-final-b1/prog.elf 8c42e020
    0x8c42e020  _end                                     +0x1028  ?
o sea el mismo sintoma de DC-002.53: el PC se va a la region de datos.)

7) QUE QUEDA PARA LA TARJETA DE LA LIMPIEZA
-------------------------------------------
La limpieza (las tres marcas a `sin-init` + la barrera verde) esta ESCRITA y PROBADA, pero no puede
aterrizar mientras 64 bytes de binario decidan entre dibujar y colgarse. La tarjeta que la aplique tiene que:
  1. partir del arbol con DC-002.53 cerrado (o con el control `checar-arranque-253.sh` en ANDA para
     BESTIA=0 con el binario NUEVO, no con el viejo);
  2. aplicar los dos `sed` del mutador (o el equivalente a mano) y compilar;
  3. exigir `checar-vram-preinit-253.sh` VERDE sobre el arbol y `checar-arranque-253.sh` ANDA con BESTIA=0;
  4. si BESTIA=0 se cuelga, NO tocar el layout para "que entre": es la senal de que DC-002.53 sigue abierto.
